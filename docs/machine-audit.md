# 研发机与目标板评估

盘点方式：2026-08-30 通过 SSH 只读检查；未停止服务、未修改配置、未清理 `/data`。

## 1. 资源与系统

| 项目 | 实测 | 结论 |
|---|---|---|
| 板卡 | Nuvoton MA35D1-IoT | ARM64 嵌入式目标板 |
| CPU | 2 × Cortex-A35 | 可支撑串口采集和轻量协议服务，不适合大型并行编译 |
| 内存 | 481 MiB；盘点时 available 约 362 MiB | 新服务应限制 RSS ≤ 80 MiB；禁止重型运行时和容器 |
| Swap | 0 | 不依赖换页；OOM 必须由限额和压力测试提前发现 |
| 根盘 | ext4 约 7.0 GiB；可用约 4.2 GiB | 程序和 1 天数据足够，必须限制日志/事件数据增长 |
| 系统 | Ubuntu 22.04 LTS，Linux 5.10.140，aarch64 | 满足 C/C++17 和 systemd 运行要求 |
| 时钟 | Asia/Shanghai；NTP active/synchronized；RTC 使用 UTC | 可生成 IEC 时间戳和可审计日志，但需监控同步状态 |
| 编译器 | GCC/G++ 11.4、Make 4.3 | 能做现场诊断编译，不建议作为主构建环境 |
| 缺少 | 常规输出中未发现 CMake、Git、libmodbus、libIEC61850 | 发布包需自带或静态链接必要库，不假设板上安装开发依赖 |
| 现有基础设施 | rsyslog、logrotate、systemd、OpenSSL 3、SQLite runtime | 日志轮转和密码学可复用；本项目不需要 SQLite |

## 2. 接口现状

### 网络

- `eth0`：UP，`192.168.3.230/24`，当前默认路由经 `192.168.3.1`；对应需求中的网口 1。
- `eth1`：配置有 `192.168.0.230/24`，但链路为 DOWN/NO-CARRIER；对应备用网口 2。
- 板卡使用厂商 `/etc/htnet/ifconfig-eth0/eth1` 和 `/etc/net.conf`、`/etc/net2.conf`，不是普通桌面 NetworkManager 工作流。
- 板上有 `/usr/sbin/dhclient`；厂商 `ifconfig-eth0/eth1` 文件含 DHCP 分支，而当前 `net.conf/net2.conf` 为 STATIC。systemd-networkd 当前未启用，因此新特权 helper 应使用受控 dhclient hook 并显式适配厂商持久化文件，不能假设 NetworkManager/networkd 接管。
- 旧配置 JSON 与当前实机存在小偏差（旧 JSON 记录 eth1 为 `.231`，内核为 `.230`），说明新系统必须把“期望配置”和“实际状态”同时显示，不能只读 JSON。

### 串口

- 存在 `/dev/ttyS0…ttyS4`；`ttyS0` 是内核 console，不可用于业务。
- 旧程序占用：`ttyS1`、`ttyS2` 和 `ttyS4`；`ttyS3` 空闲。
- 产品已确认按 485-1 → ttyS1、485-4 → ttyS4 接线；当前无 485 线，后续实机阶段验证电气与收发。
- `/proc/tty/driver/serial` 盘点时 ttyS1/ttyS2 的 TX 有增长，RX 均为 0；无法据此证明 PD1000 已连接或 RS-485 收发方向正确。
- 实施时必须在停止旧 Main.py 后独占端口，并用真实接线或隔离仿真器验证。不得并发打开同一 tty 做测试。

## 3. 受保护与可替换进程

### 绝对保留

- `frpc.service`：systemd 管理的 FRP 客户端。
- `4g_server`：4G 服务进程。
- 板卡的 `sysrst`、watchdog、网络启动脚本等系统能力。

项目安装、网络配置、服务重启和压力测试不得终止、改名、覆盖其文件或接管其端口/设备。

### 后续切换时可停止

- `python Web.py`：盘点时 RSS 约 26 MiB，监听 8889。
- 子进程 `python Main.py`：盘点时 RSS 约 27 MiB，监听 502，并占用 ttyS1/ttyS2/ttyS4。
- root crontab 的 `@reboot sudo /data/run.sh &`：新服务验收通过后才能禁用，避免重启后旧服务重新抢占端口。

当前设计阶段没有停止上述旧服务。正式切换必须先记录 PID/端口/设备归属并只终止匹配 `/data` 工作目录的旧进程，不能使用宽泛的 `killall python`。

## 4. `/data` 旧实现评估

`/data` 总量约 1.1 MiB（另有当日日志约 575 KiB），主要是 Tornado + pymodbus + pyserial 的 Python 网关。

### 可复用的知识

- 板卡串口命名、双网口持久化文件和厂商启动脚本。
- 蓝色主色、卡片式主页、网络/串口/日志表单的信息组织。
- Modbus TCP/RTU 主从同时运行的板卡可行性样例。
- 原子写临时文件再替换的思路。

### 不复用的实现

- 无登录、无 CSRF，Tornado `debug=True`。
- 重启服务、重启设备等危险动作由 GET 触发。
- Web 请求参数直接进入 root 脚本；旧 IP 脚本写配置后立即重启，没有回滚。
- 所有进程以 root 运行。
- 日志每次写入都扫描并删除旧文件，只保留当天，且缺少级别、组件和大小轮转。
- 配置修改缺少 schema、并发版本、完整服务端校验和事务边界。
- `run.sh`/crontab 管理进程，Main.py 是 Web.py 子进程，故障与重启边界不健康。
- 依赖 numpy/pandas/openpyxl 等与新运行目标无关，增加内存和供应链面。

因此旧代码只作为只读参考，不复制到新源码树。

## 5. 容量估算

### 运行时

- 旧 Python Web + Main 合计约 53 MiB RSS。停止后可释放这部分内存。
- 目标：C++ 主服务 ≤ 80 MiB RSS，最好稳定在 40–60 MiB；systemd `MemoryMax=128M`。
- 单份 3615 寄存器约 7.1 KiB；即使保留多个快照和 Web 序列化缓冲也不是内存瓶颈。
- 115200 bps 下每轮约 7.5 KiB 响应，纯线速小于 1 秒；6 秒周期对 CPU/串口带宽充裕。
- PRPD/PRPS 在浏览器绘制，避免目标 CPU 生成图像。

### 磁盘

- 紧凑帧约 7.3 KiB。
- 5 分钟一帧：约 288 帧/天，约 2.1 MiB/天。
- 极端每 6 秒触发一帧：约 14,400 帧/天，约 105 MiB/天。
- 日志按 5 MiB × 7 轮的上限约 35 MiB（压缩后通常更少）。
- 在当前 4.2 GiB 余量下足够，但事件风暴、崩溃转储和升级包仍要求磁盘低水位保护。

## 6. 是否足够支撑开发

结论分两层：

- **作为产品运行机与硬件集成机：足够。** 资源可支撑轻量单守护进程、三种工业协议、静态 Web、日志和一天数据。
- **作为主要编码/构建机：不够理想。** 双核 A35、481 MiB、无 Swap、缺 CMake/Git；在板上并行编译大型 C/C++ 依赖会慢且有 OOM/eMMC 磨损风险。

推荐研发拓扑：

1. Codex/Luna 在当前项目工作区实现和运行单元/模拟器测试。
2. 工作站或 CI 用固定 aarch64 工具链构建发布包。
3. 通过 SSH 部署到 `192.168.3.230` 的版本目录。
4. 只在板上做协议、串口、网络回滚、资源和长期运行验收。

若必须临时在板上编译，只允许低并发（`-j1`）诊断构建；不建议把创建 Swap 作为常规方案。

## 7. 当前不可验证项

- PD1000 未产生串口 RX，31 笔请求/响应和 6 秒轮询尚未实测。
- eth1 无载波，双网口切换和路由尚未实测。
- 未安装 IEC 61850 协议栈，102 端口和目标客户端互操作尚未实测。
- 旧服务占用 502/ttyS1/ttyS4，设计阶段不能并行启动新协议服务。
- 当前远程 Git 仓库无 refs，判断为空仓库；本地设计文件尚未提交或推送。
