# v3.0 实现状态与需求审查

## 0. 结论与边界

当前分支是 `v3.0`。主需求足以开始分模块开发，但不足以在没有协议补充和实机联调的情况下认定整机交付完成。

本轮已经实现并测试**独立的数据处理核心**，不是整机 v3.0：新代码位于 `src/v3/`，尚未链接到 `uhf-gatewayd`。直接运行现有守护进程仍是原来的单 PD1000 行为，不能用于验收三合一系统，也不能认为已具备第九章的激活门禁。没有变更真实目标板、`/data` 服务、frpc、4G 或生产配置。

## 1. 唯一开发基准

1. `spec/v3.0/嵌入式开发需求书-综合监测管理机-v3.0.docx`：当前主需求，含第八章对历史笔误的修正。
2. `spec/v3.0/电缆局放通信规约.docx`：新局放设备的原始规约，用于补充寄存器和设备参数定义。
3. `spec/reference/开发需求20240829-1.docx`：只用于核对电流/温度历史报文，不自动覆盖新需求。
4. 旧 v1.0、PD1000 Excel、`luna-implementation-brief.md`、`requirements-baseline.md`、旧架构/计划等，只作历史实现参考；与本次 v3.0 不一致的内容不得继续当作产品需求。

本轮没有改写任何原始 DOCX/XLSX，下面的临时实现选择不代表需求方已经确认。

## 3. 已测试但仍需产品确认的选择

- 电流编码和电流/温度换算倍率必须由调用方明确传入；不把未知单位猜成 A、mA 或 0.1℃。当前转换辅助函数按一组通道同一线性倍率处理；若 CT/传感器倍率逐通道不同，需先补逐通道转换配置。
- 新局放均值/峰值使用 mV；谱图只保留有符号原值，不标成 dBm，也不继承 PD1000 的 `FFBA/FFBC` 特殊值含义。
- 启动不足 50 个有效样本时，调用方必须选择“先报样本不足”或“按已有样本计算”。当前窗口按每相最近 50 个有效采样推进；无效样本跳过，不清空历史。断线/重新配置是否重置，需要进一步确认。
- 除零、溢出、非有限值标成无效；负均值不平衡度的分母提供按原公式、取绝对值、拒绝非正值三种显式策略，没有偷偷选生产默认值。
- 当前 `In/IN/TN` 输出百分数数值，例如 25 表示 25%；`Qa/Qb/Qc` 保持原公式比值，例如 0.25。需要与上位机确认数值语义。
- 电流/温度上行使用 **0x03** 是依据历史方案提出的配置；主需求 §5.1 对该区功能码未像局放 0x04 那样明确写出，发布前需确认。
- 无效 float32 可明确选择规范化 quiet NaN 或 Modbus 异常 04；缺失局放原始字/未知遥信状态目前返回异常 04，不伪造零值。整机必须补充数据时效和失效后的上行约定。
- 遥信按主需求表格顺序生成 0..14 的线地址，表版本为 1；上位机应使用 `discrete_point_table_csv()` 的结果。编号可由 AI/程序决定，不要求需求方手工编表；配置变化不能偷偷重排地址。尚未提供网页导出入口。
- 每次请求读取调用方提供的不可变快照；运行时仍须保证快照发布、锁/所有权和每路时间戳的一致性。

## 4. 待澄清清单（按对联调的影响排序）

1. **电流/温度完整下行定义**（§3.2/3.3、附录 C/D）：两台设备的波特率、校验/停止位；电流 signed/unsigned、A/mA/CT 比例及逐通道倍率；温度 152 究竟表示 152℃ 还是 15.2℃；量程和设备故障码。温度 1/3/5 号寄存器已经明确，不是缺项。
2. **谱点物理含义**（§3.1/8）：单位、倍率、有效范围、无信号/未刷新/传感器故障编码。特征值 mV 不能直接推出谱点也为 mV。
3. **无效和过期数据的对外表示**（§5/7）：Modbus 返回 NaN、异常码还是旧值加状态；多路异步数据多久算过期；某个分段失败是否允许发布部分通道；存档如何标明各路采样时间和质量。
4. **计算边界**（§4）：除数为零怎么办；负温度均值如何定义 TN；百分比线上传 25 还是 0.25；不足 50 次、读取失败、断线恢复、重启/修改周期时如何处理统计窗口。
5. **通信和报警时序**（§3/5.1/7）：响应超时、重试三次是总共三次还是额外三次、连续失败几次置位/几次恢复、退避上限；三秒间隔按上次开始还是结束；12 个阈值的默认值及无效数据时报警保留/复归规则。是否需要回差、防抖可由需求方确认，不擅自改变现有严格“>”条件。
6. **IEC 61850 交付点表**（§5.2）：列到具体 DO/DA、类型、单位、q/t、数据集、报告控制块及客户端验收用例。“MMXU/STMP 类”还不是完整互操作接口；AI 可以生成候选 ICD，但需指定上位系统和报告要求。相关性、谱图、全部计算值哪些需要上送也应列明。
7. **激活规范和制造配置**（§9）：确定序列号的真实来源、标识拼接格式/主路径、厂家密钥注入与轮换方式；只保存一个“已激活”布尔值不能替代启动时重新核对设备绑定。文中 20 字符、每组 5 个与 `XXXX-XXXX-XXXX-XXXX` 格式矛盾，Base32 字母表、去填充和金样本需固定。普通固件密钥可被提取的风险原文已经承认，不能把它验收为绝对防复制。
8. **目标板与配置边界**（§2/5.4）：确定最终 CPU/发行版、交叉工具链、四个 tty 与网卡名字、RS485 方向控制方式、Wi-Fi/4G 模块及其管理接口。现有构建基准是 AArch64；不能据“ARM/MIPS”推断两个平台都已验证。明确 v3 是否继续保留旧 HTTPS/FTP/事件能力，避免把旧简报要求默认带入。
9. **报文查看表述**（§5.5）：建议改成“仅使用有界内存缓存，最多 N 条或 M 字节，不落盘，慢客户端丢旧数据”。“保留最近若干条”与“完全不写入内存”无法同时成立。
10. **验收输入和阈值**：补三台设备的脱敏正常/故障报文、实测值对照、上位机读写/报告期望、允许刷新延迟/磁盘内存上限、连续运行时长。主机模拟测试不能替代这些实机验收。

以上多数问题不阻止框架和纯逻辑开发，但不能靠 AI 猜定之后直接声明整机完成。类名、文件拆分、点表生成器、缓存具体容器等普通设计细节，可继续交给实现者决定。

## 5. 本地验证

在仓库根目录：

```sh
cmake -S src/v3 -B build/v3 -DCMAKE_BUILD_TYPE=Debug
cmake --build build/v3 --parallel 4
ctest --test-dir build/v3 --output-on-failure

cmake -S src/v3 -B build/v3-release -DCMAKE_BUILD_TYPE=Release
cmake --build build/v3-release --parallel 4
ctest --test-dir build/v3-release --output-on-failure

cmake -S src/v3 -B build/v3-sanitize -DCMAKE_BUILD_TYPE=Debug -DUHF_V3_SANITIZERS=ON
cmake --build build/v3-sanitize --parallel 4
ctest --test-dir build/v3-sanitize --output-on-failure
```

本轮上述三个构建各有 3 个 CTest 测试，均已在主机执行通过。Release 测试不依赖会被 `NDEBUG` 关闭的 `assert`。这是逻辑/协议测试，不是实际三路串口、多客户端网络、IEC 或实机稳定性测试。

`.github/workflows/v3-host-validation.yml` 分别运行旧产品 host 回归和新核心 Debug/Release/ASan+UBSan 测试。是否通过以对应提交的 Actions 结果为准；不要把某个旧提交的绿灯当成当前提交已通过。

## 6. 后续最小闭环

先补可注入时钟的三路采集调度及 PTY 设备模拟器，证明局放顺序/间隔/部分失败不阻塞电流和温度；再将核心接入不可变快照、现有 TCP/RTU 服务、带 q/t 的 IEC 模型、三合一 Web 和存储；最后完成激活总门禁、板级适配和整机验收。

激活门禁必须在部署试运行前覆盖全部新旧核心服务；未经这一阶段，不能对外提供“v3.0 发布包”。
